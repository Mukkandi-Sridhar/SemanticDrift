Section 1: Name-collision check for "semantic drift"
Semantic drift – existing uses: In NLP/ML, "semantic drift" has long been used in two main ways. One usage is in bootstrapped information extraction, where iterative pattern learning can "drift" from the intended meaning. For example, Li et al. (EDBT 2014) note "semantic drift is a common problem in iterative information extraction" – as iterations proceed, extractions may shift from the target concept to other concepts. A second usage is in long-form text generation: Spataru et al. (NAACL 2024) show that LLMs often generate correct facts first and "drift away" into incorrect ones later, coining a "semantic drift score" to quantify this degradation. In survey and engineering contexts, "semantic drift" is also used broadly (e.g. by data teams) to mean a model's output gradually moving away from intended meaning over time. The term is distinct from but related to "concept drift" (distribution shifts over time) and other uses (e.g. vocabulary change in linguistics).
Semantic drift in tool/agent context: We found no prior academic use of "semantic drift" specifically for tool descriptions, APIs or agents. In the LLM agent literature, similar problems have been noted (e.g. tool-selection errors due to ambiguous docs) but they are described with terms like "tool poisoning" or "misuse", not as "semantic drift." We did find related notions of tool misinterpretation in blog posts or security docs (e.g. "tool description poisoning" or "tool intent manipulation"), but no published term exactly matches "semantic drift" for tool descriptions.
Recommendation on naming: Because "semantic drift" already has established meanings (especially in IE and text-generation), using it for our new phenomenon risks confusion. If used, it must be carefully defined (e.g. "semantic drift of tool description = divergence between developer intent and model's interpretation of a tool's natural-language description"). However, a more distinctive name might be better. Possible alternatives (none of which appear in the literature) include "Tool Semantic Misalignment," "Tool Intent Drift," "API Documentation Drift," or "Tool Description Misinterpretation". We checked these terms and found no existing uses in the LLM or API contexts (searches turned up unrelated uses of "semantic misalignment" or "documentation drift"). For example, "Tool Intent Drift" and "API Documentation Drift" do not appear in research titles or abstracts, so they seem free of collision. If we rename, we should briefly define it (e.g. "the interpretation of a tool's description drifting from intended meaning") to avoid overlap with the old uses in text or IE.

Section 3: Novelty gap analysis
What is done: Prior work has shown that tool description quality matters and that LLM agents often choose tools incorrectly. In particular, recent papers (EASYTOOL, DRAFT, TRUSTDESC, etc.) improve documentation or use agent feedback to refine it. Benchmarks (MetaTool, BFCL, MCPToolBench, LiveMCPBench) have tested tool selection and calling at scale. Security work (MCPTox, Jamshidi et al.) has shown that adversarially altering tool descriptions can hijack agents. Techniques for robustness (e.g. Flip-Flop) show LLMs can be sensitive to prompt wording.
What is not done: However, no work has explicitly conceptualized or measured how benign ambiguities or phrasing in tool descriptions cause systematic errors. Existing efforts focus on rewriting docs or adding missing info, but do not categorize the failure modes or quantify how much agents "drift" from intent as description quality degrades. In particular, no study has used controlled perturbations of tool descriptions to measure tool-selection accuracy or parameter errors. Our proposed taxonomy (over-generalization, over-specialization, contextual misalignment, parameter hallucination) is novel: it distinguishes types of misinterpretation not isolated in prior work. While DRAFT/Trace-Free show that clearer docs help, they do not analyze why the original docs misled the model (beyond showing outcomes). Similarly, no survey has defined "semantic drift" in tool context or evaluated how reliability degrades as docs become more ambiguous.
Novel contribution (2–4 pp): Our most defensible new contribution is a systematic evaluation of how LLM agent performance degrades when tool descriptions are perturbed by controlled semantic changes. Concretely, we will create ambiguity-variants of tool descriptions (one per drift type) and measure tool selection/parameter accuracy across models. This reveals which drift modes are most harmful and to which models. In short: a taxonomy and empirical measurement of "semantic drift" in tool descriptions.
Closest prior works and positioning:
* Qu et al. (2025, DRAFT): Iteratively refines tool docs via agent feedback. They demonstrate improving docs improves performance. We position our work as complementary: rather than automatically fixing docs, we analyze the causes of misinterpretation in the original docs.
* Guo et al. (2026, Trace-Free+): Rewrites tool descriptions to optimize agent reliability. They implicitly acknowledge that poor docs hurt performance. We differ by explicitly introducing the notion of drift types and measuring performance under original vs perturbed docs, rather than only reporting gains from rewriting.
* Huang et al. (2023, MetaTool): Studies tool selection errors among similar tools, noting that brief descriptions cause confusion. Our novelty is adding a structured taxonomy of such confusion (e.g. over-general vs. over-specialized) and quantifying it under controlled perturbations. We will highlight that while MetaTool identifies the problem, it did not systematically categorize or stress-test it.

Section 4: Methodology guidance from prior work
Controlled perturbations: No standard "perturbation suite" exists for tool docs, but inspired by previous ideas one can apply: (a) Information removal: drop key details (e.g. omit domain-specific constraints) to induce over-generalization errors. (b) Over-specification: add restrictive qualifiers or examples so the tool seems inapplicable (causing over-specialization). (c) Rephrasing/context changes: change wording or add misleading terms (to induce contextual misalignment, e.g. "deposits" vs "archives"). (d) Hallucinatory parameters: insert extra irrelevant parameters or schema fields (reflecting parameter hallucination). For example, we might take an existing MCP schema and introduce a spurious parameter or substitute synonyms. Prior security work often injects malicious instructions into descriptors; we will do similar edits but non-malicious (e.g. rewording). The DRAFT/EasyTool papers did not enumerate perturbation types, but they did note errors like missing examples or confusing names; we will use those as guides to design our variants.
Metrics: We will measure (a) Tool-selection accuracy: fraction of tasks where the agent picks the correct tool (from the gold set). Metrics include top-1 accuracy and possibly Top-k accuracy if we allow the agent to see multiple tools. For multi-step tasks, we use task success rate (all required tools used correctly). (b) Argument correctness: for calls using the correct tool, measure whether each parameter value is valid (we can use F1 or exact-match against the schema and ground-truth parameters as in Trace-Free: subtask- and query-level success). (c) Robustness/DRIFT rate: defined as the drop in accuracy from clean to perturbed descriptions (per drift type). If running stochastic agents, use pass@k or pass^k (chance of success over k runs) to capture variability.
Dataset sizes & models: Prior benchmarks range from tens to thousands of tasks. For a credible workshop study, 30–100 diverse tasks is common (e.g. τ-Bench uses 95 tasks, AssetOps has 140+ queries). We should create at least ~50 tasks covering several domains. Since we test multiple LLMs (≥3), each with multiple runs, total calls might be a few hundred, which is acceptable. Similarly, prior studies often evaluate on 3–10 models (e.g. [102] tested 10 frontier models; τ-Bench used 3†). For balance, we should use ~4 models (see Section 5). We will randomize task order to avoid sequence effects.
Common pitfalls: Reviewers often warn against "toy" tasks or leaking answers. Ensure tasks are realistic (use or adapt from AssetOpsBench, MCPToolBench etc) and that the gold tool is not directly mentioned in the prompt. Avoid giving the agent training examples with the same tool usage if doing multiple runs. Also, when measuring robustness, be careful not to tune the model on perturbed prompts (to simulate real deployment shifts). We should also report variance (e.g. pass^k) rather than a single-run success rate, since randomness in LLMs can hide instability. Finally, we must clearly define our metrics (as above) and probably include human inspection of sample failures to confirm taxonomy labels. (As the LiveMCPBench authors noted, automatic evaluation can be noisy, so we may need some manual vetting.)

Section 5: Model selection
Recent tool-use papers evaluate both closed and open models. Based on the literature: GPT-4 (latest OpenAI) is almost universally included (ToolBench, LiveMCP, etc). Anthropic Claude models (Sonnet/Opus) are also widely used. Among Google/others, Gemini (now Gemini 1/Gemini 2) is emerging. For open-weight models, Llama-3 (70B) is a strong performer (used in DRAFT and TRACE-FREE evaluations) and is publicly available. As a smaller open model, Mistral-7B or Llama-2-70B can be considered, but Llama-3's larger variant is more directly comparable to GPT-4-level performance. We recommend at least GPT-4o (latest OpenAI model, closed), Claude Sonnet-4 (Anthropic's high-capacity model, closed), Llama-3-70B (open), and Qwen-32B or Mistral-7B (open-ish smaller model) as diversity. These choices align with recent evaluations. (All are "current" as of late 2026; e.g., GPT-4o and Claude-4 were released in 2025-26, Llama-3 in late 2023.) Each has a reasonably sized interface for function-calling (check API or open repos for exact version names).

Top 5 takeaways for my paper
* Differentiate "semantic drift": The term is pre-used for IE and text-gen. If kept, define it strictly for tool descriptions. Otherwise, a new name (e.g. "Tool Intent Drift") avoids confusion.
